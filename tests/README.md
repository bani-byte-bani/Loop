# LOOP CONSOLE E2E テスト

実際にブラウザでアプリを動かし、**合成した音を録音させて結果を数値で確かめる**テストです。
同期精度のように「動いているように見えるが数値がおかしい」不具合を捕まえるためのものです。

## アプリ本体はビルド不要のまま

このディレクトリは**開発時にだけ使う道具**で、アプリの配信には一切関与しません。

- `index.html` / `sw.js` / `manifest.json` は従来どおり素の HTML/CSS/JS
- GitHub Pages は `tests/` を無視するので、公開されるファイルは変わりません
- `node_modules/` はコミットしません(`.gitignore` 済み)

## 使い方

```bash
cd tests
npm run setup     # 初回のみ: playwright と Chromium を入れる
npm test          # すべて実行
npm test -- tuner # 名前に一致する spec だけ実行
```

Chromium が既にある環境では、場所を明示できます。

```bash
LOOP_TEST_CHROMIUM=/path/to/chrome npm test
```

すべて成功すると終了コード 0、1 つでも失敗すると 1 を返します。

## 実行にかかる時間

**フルセットで数分かかります。** 録音は実時間で流れるため、たとえば
120BPM / 4 小節の録音 1 回につき 8 秒待つ必要があります。
各 spec では検証に支障のない範囲で BPM を上げて短縮しています(240〜300BPM など)。

急ぐときは spec 名で絞り込んでください。

## テストの構成

| ファイル | 何を守っているか |
|---|---|
| `01-loop-length` | ループ長がテンポからの理論値と 1 サンプルも違わないこと |
| `02-latency-rotation` | 録音補正が意図した量だけバッファを回転させていること |
| `03-capture-gaps` | 切り出したバッファに無音の穴が無いこと(先読みが足りているか) |
| `04-first-loop` | 録音直後の 1 周目が正確な時刻に予約されていること |
| `05-transport` | 録音中のトラック切替で尻切れしないこと / 同時録音の拒否 |
| `06-rec-align` | 案内どおり参照トラックの周回頭から録音が始まること |
| `07-auto-adjust` | しきい値を超えた最初の音が小節頭に揃うこと |
| `08-metronome` | ランプの点灯順 / 無音のあいだ鳴り録音で止まること / 手動オンは 1 拍目から |
| `09-tuner` | 音程検出の精度(cent 単位)と入力チャンネル選択 |
| `10-tracklist` | 固定長表示のループ幅と再生ヘッド |
| `11-mixer-overdub` | 音量・ミュート / CLEAR 取消 / 重ね録り / WAV 書き出し |
| `12-reliability` | クロック断の検出 / AudioContext の復帰 / MIDI タイムアウト |
| `13-key-mappings` | 記号キー(`"` `<` `&`)でマッピングが壊れないこと |
| `14-clock-stability` | 外部クロックのテンポ推定が配達の遅れに引きずられないこと / 出力が直結経路であること |
| `15-midi-transport` | MIDI の Start / Continue / Stop で再生が止まる・戻ること |

## 書くときに踏んだ落とし穴

これらは実際に一度間違えて時間を溶かした箇所です。同じ轍を踏まないように。

- **検証用の正弦波に 440Hz を使ってはいけない。**
  2 秒バッファに 880 周期ちょうど収まるため、バッファを回転させても波形が
  連続のままで継ぎ目が検出できません。`443.3Hz` のように非整数周期になる
  周波数を使います(`SIGNALS.spliceProbe()`)。

- **`createBuffer` のフックは同じ長さのバッファを複数拾う。**
  切り出し後に回転で新しいバッファを作るため、同じ長さのものが 2 つ並びます。
  `>=` で比較して**最後のもの**(= 全処理を終えたもの)を採ってください。

- **リバーブのインパルス応答もフックに引っかかる。**
  2.2 秒ぶんのバッファが作られるので、単純に「一番長いもの」を採ると
  録音バッファではなくこれを拾います。録音の直前に位置を記録して、
  それ以降に作られたものだけを見ます(`markBuffers`)。

- **エフェクトは次の小節頭まで予約される。**
  トグルを押した直後に値を確認しても変わっていません。1 小節ぶん待ちます。

- **カウントは手動オンだと次の小節頭まで鳴りません。**
  オン直後を短時間で確認すると「鳴っていない」と誤判定します。接続直後だけは
  クロックがパルス0から始まって既に頭が揃っているため待ちません。この差を
  忘れると、待ち時間の見積もりを 1 小節ぶん間違えます。

- **クロック系のテストは「配達を遅らせる」だけにして、`timeStamp` は正確な格子を渡す。**
  実機の MIDI もこの形(メッセージ自身の時刻は正しいが、ハンドラの実行は遅れる)なので、
  タイムスタンプごとずらしてしまうと、直したはずの不具合を再現できません。

- **テンポ推定の窓が埋まるまでは判定に使わない。**
  1 小節(96 パルス)ぶん貯まるまで表示は `---` のままです。採取したサンプルの
  先頭ぶんは捨ててください(`14-clock-stability` の `settled()`)。

- **合成音声の取りこぼしは 10ms 単位で起きる(テスト環境由来)。**
  テストの音は `別AudioContext → MediaStream → getUserMedia → アプリ` という
  実時間経路を通ります。MediaStream の音声フレームは 10ms なので、負荷が高いと
  フレームごと丸ごと落ちます。欠落の最長が毎回きっちり 10.0ms なのがその証拠で、
  単独実行では 0.000% です。**実機のマイク入力はこの経路を通りません。**
  `03-capture-gaps` は「1回の欠落の長さ」を主判定にしてこれを避けています
  (構造的な穴は数百ms規模になるので確実に区別できます)。総量の割合で
  判定しようとすると、全スイート実行時だけ落ちる不安定なテストになります。

- **headless では Web MIDI の権限プロンプトが解決しません。**
  `harness` が常に `requestMIDIAccess` を差し替えます。外部クロックの
  テストは偽の MIDI 入力を作り、`onmidimessage` を直接叩いて駆動します。

## 環境について

- ページが「非表示」扱いになるとタイマーが絞られ、タイミング系の測定が
  不安定になることがあります。失敗が続く場合は他の重い処理を止めてから
  再実行してください。
- `04-first-loop` の余裕(ms)はマシンの負荷に左右されます。値そのものより
  **正の値であること**(= 締切に間に合っていること)を見ています。
